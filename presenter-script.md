## Slide 3 — What is GitHub—and why might IDs use it?

A simple way to think about GitHub is as an online home for project files. It keeps revisions together and gives people a way to collaborate. Developers and coders have traditionally used it to manage software projects, so the terminology can sound technical. But instructional designers do not need to become software developers to benefit from the same practices. In this new era of vibe coding, AI can help us create a custom interactive from a course-design idea. GitHub gives that project a place to live, change over time, and be shared.

## Slide 4 — AI makes custom course interactives easier. What happens next?

AI has made it easier than ever to create a custom interactive for a course. We can make something that fits a learning activity instead of settling for a generic tool that a traditional LMS or an expensive plugin might offer. If you simply use AI to create a custom HTML interactive and upload it into a course, that might work well for just a single semester. But what happens when changes need to be made? Who updates it next semester? What happens when the course is copied, or when another instructional designer inherits it? And six months from now, how will we know what changed? GitHub provides a centralized location for coded projects to live where they can be collaboratively edited and maintained in a sustainable fashion.

## Slide 5 — The LMS is where students experience it. GitHub is where the project lives.

These are some of the problems we are going to use GitHub to help solve today. The LMS is still where students encounter the vast majority learning experience: the instructions, the activity, and the course context. GitHub is great for interactive objects, vibe-coded projects, or other custom web objects that you may want to insert into your LMS. It just gives those projects a home outside an individual course shell, making it easier to share, document, revise, and maintain these types of projects.

## Slide 6 — GitHub supports the project across its life.

GitHub can be a helpful tool when it comes to maintaining the lifecycle of a custom-built learning resource because it provides a central repository in which your project can live. Say we create an interactive using AI and vibe coding. GitHub provides a platform and a standard operating procedure for ensuring the longevity of that project into the future. Once a project is uploaded to Github, you can document it in a README so another person knows what it is, why it exists, where it is used, who owns it, and how to update it. Github is also a version control system, meaning it maintains a record of all changes made to the project, who made those changes, and why those changes were made, with the ability to revert back to previous versions as needed. As courses and needs change, Github's versioning system ensures that projects can be safely updated by mutiple contributors without overwriting any previous changes made GitHub also offers a free web hosting service--Github Pages-- which allows you to give any project a web address, then deliver it through an LMS, using a single stable URL that does not change from semester to semester or course copy to course copy. When changes are made, they are made centrally to the project folder and then pushed out the LMS through that single, stable URL.

## Slide 7 — What happens next semester?

Imagine you vibe-coded an interactive element for your LMS, say, a scenario-based activity that appears in four sections of the same course. It works great until one day an acronym frequently referenced in the interactive changes. If the interactive is copied independently into four LMS shells, someone has four places to find and update. Then each copy needs to be checked to make sure it still works. If those four courses display one centrally hosted project, the team updates the source once and republishes it. The courses continue to display that shared version. That is the practical value: fewer scattered copies to track when something changes.

## Slide 8 — What happens when someone else inherits the course?

Another scenario. Imagine one instructional designer creates a custom interactive. Two years later, another ID inherits the course. They need to know where the source is, what changed, how it was published, and who owns it. A README provides the context and update instructions. The repository keeps the project files together. Commit history gives the next person a record of changes and their reasons. Shared ownership means the work does not depend on the original creator's personal account or memory. The goal is not just to save code; it is to make what we built understandable and maintainable by someone else.
