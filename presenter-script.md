## Slide 3 — AI makes custom course interactives easier. What happens next?

AI has made it easier than ever to create a custom interactive for a course. We can make something that fits a learning activity instead of settling for a generic tool. But building it is only the beginning. Where does the project live after we make it? Who updates it next semester? What happens when the course is copied, or when another instructional designer inherits it? And six months from now, how will we know what changed? Those are course-development and handoff questions—not coding questions.

## Slide 4 — Canvas is where students experience it. GitHub is where the project lives.

That is the problem we are going to use GitHub to help solve today. Canvas is still where students encounter the learning experience: the instructions, the activity, and the course context. GitHub gives the project behind a custom interactive a home outside an individual course shell. That separation can make the work easier to share, document, revise, and maintain.

## Slide 5 — GitHub supports the project across its life.

Think about the lifecycle of a learning resource. We create an interactive—AI and vibe coding can make small, custom pieces much more approachable. We document it in a README so another person knows what it is, why it exists, where it is used, who owns it, and how to update it. We version it with commits, which record what changed, when, and why. We publish it with GitHub Pages to give it a web address, then deliver it through Canvas. And we maintain it as courses and needs change. The project lives in a repository: a shared folder for its files and history. If you want to adapt an existing project, you can make a fork—a separate copy to work from.

## Slide 6 — What happens next semester?

Imagine this interactive appears in four sections of the same course, and the support phone number changes. If the interactive is copied independently into four Canvas shells, someone has four places to find and update. Then each copy needs to be checked to make sure it still works. If those four courses display one centrally hosted project, the team updates the source once and republishes it. The courses continue to display that shared version. That is the practical value: fewer scattered copies to track when something changes.

## Slide 7 — What happens when someone else inherits the course?

Imagine one instructional designer creates a custom interactive. Two years later, another ID inherits the course. They need to know where the source is, what changed, how it was published, and who owns it. A README provides the context and update instructions. The repository keeps the project files together. Commit history gives the next person a record of changes and their reasons. Shared ownership means the work does not depend on the original creator's personal account or memory. The goal is not just to save code; it is to make what we built understandable and maintainable by someone else.
